API tokens vs OAuth 2.0 (3LO)

The two ways a program can act as you in Jira, how they differ, why each edition uses the one it does, and what scopes, consent and grants mean.

Option 1: an API token (Local edition)

You create a token at id.atlassian.com → Security → API tokens and give it, with your email, to the program. Every request carries Authorization: Basic base64(email:token).

  • Power: the token can do everything you can do in every Atlassian product. No scopes.
  • Fine for: a program running on your own computer, for you.
  • Not fine for: a shared website. Asking strangers to paste all-powerful tokens into your server would make you a juicy target and them dependent on your honesty.

Option 2: OAuth 2.0 authorization code grant ("3LO", Cloud edition)

The user signs in at Atlassian and approves specific permissions for your app. Your server receives tokens that only allow those permissions, only on the sites the user chose, and that the user can revoke any time. The full flow is in Signing in with Atlassian.

There is no write scope: the app cannot change anything in Jira. These are "classic" scopes; Atlassian also offers finer "granular" scopes, which are not needed here.

Grants: resource-level vs account-level

When registering the app you choose:

  • Resource-level (chosen for this app): the user picks one site on the consent screen; the token works only there. Least privilege.
  • Account-level: the grant covers every site in the customer's account.

Atlassian keeps one grant per app per Atlassian account. Consenting again for another site adds it to the same grant.

Finding the site: accessible-resources

GET https://api.atlassian.com/oauth/token/accessible-resources
Authorization: Bearer <access token>
→ [ { "id": "1324a887-…", "name": "axismaxlife", "url": "https://axismaxlife.atlassian.net",
      "scopes": ["read:jira-work", "read:jira-user"] } ]

The id is the cloudId used in every API URL. The app stores the list in jira_sites and lets you switch the active site in settings.

Refresh tokens

With offline_access, the token response includes a refresh token. It is rotating: each use returns a new one and disables the old (10-minute reuse leeway; reuse outside it may revoke the grant). The app's concurrency-safe refresh is in Refreshing and rotating tokens.

Things organisations can control

  • Distribution: a new app works only for its developer until set to Sharing (see The developer console).
  • Admin policies: organisation admins can block or require approval for third-party apps on their sites (admin.atlassian.com). A colleague may see "ask your admin" even though the app works.
  • Revocation: users revoke at id.atlassian.com → Connected apps; admins uninstall the app from the site.

How the page knows which edition it is in

When the page loads, detectMode() in src/client/api.ts runs:

  1. If the URL contains ?demo → demo.
  2. Otherwise it fetches api/config. If the answer is JSON with "edition": "cloud" → cloud; any other JSON → local.
  3. If there is no server (GitHub Pages returns a 404 HTML page) → demo.
export async function detectMode() {
  if (new URLSearchParams(location.search).has('demo')) return { mode: 'demo', config: { configured: false } };
  try {
    const res = await fetch('api/config', { cache: 'no-store' });
    if (res.ok && (res.headers.get('content-type') || '').includes('application/json')) {
      const config = await res.json();
      return { mode: config.edition === 'cloud' ? 'cloud' : 'local', config };
    }
  } catch { /* no server: static hosting */ }
  return { mode: 'demo', config: { configured: false } };
}

The rest of the frontend asks mode before doing anything edition-specific: which settings form to show, whether to open a live stream (local) or register a service worker (cloud), whether data is real or generated.

Why one codebase for three editions

  • One product: a fix or feature lands everywhere at once.
  • One API contract: both servers answer the same paths with the same JSON shapes, so the page does not care which one it talks to.
  • One Jira brain: src/core holds the Jira logic for both servers. It was verified to give byte-identical results to the original Local code against a real Jira site.

Choosing

Rule of thumbIndividual who cares most about privacy: Local. A team that wants zero installation: Cloud (your own instance, or one shared URL). Curious visitors: Demo. A company that does not want a personal account holding its tokens: deploy its own Cloud instance with the playbook.

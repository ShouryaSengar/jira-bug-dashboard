Git, GitHub and GitHub Pages

How the source code is versioned and published, the branches and tags this project uses, how the free demo site is deployed by GitHub Actions, and safe habits that protect working code.

⏱ 9 min readGuide 41 of 47

Git in five ideas

  1. Repository: a folder whose full history Git remembers.
  2. Commit: a saved snapshot with a message (git commit -m "…"). Each has an id like dcb9cb2.
  3. Branch: a movable name pointing at a line of commits (main, feature/…).
  4. Tag: a fixed name for one commit, used to mark releases (v1-local-stable).
  5. Remote: a copy elsewhere (GitHub, called origin); git push sends commits there, git pull fetches them.

This project's branches and tags

NameKindPurpose
mainbranchstable Local edition and the Pages demo; every push deploys the demo
v1-local-stabletagthe exact working state before the Cloud edition began
backup/local-stablebrancha second safety copy of that state
feature/cloudflare-web-editionbranchthe Cloud edition, developed separately until merged

The feature branch was checked out in a separate folder with git worktree, so the running local app (served from the main folder) was never disturbed while the Cloud edition was built.

git tag -a v1-local-stable -m "Stable local edition"
git branch backup/local-stable
git worktree add -b feature/cloudflare-web-edition ../jira-bug-dashboard-cloud main

Everyday commands

git status                         # what changed
git add path/to/file               # stage specific files (avoid "git add ." without looking)
git commit -m "Explain the change"
git push origin feature/…          # publish the branch
git log --oneline -5               # recent history
git diff --cached                  # review what you are about to commit

Safe habits

  • Never commit secrets. .gitignore lists .dev.vars, node_modules, dist, site, dist-assets, .wrangler. Before each commit, review git diff --cached.
  • Never force-push shared branches, never reset away commits you did not make.
  • Tag before big changes; work on a branch; merge only after tests pass.
  • Ask before pushing if someone else owns the repository (pushing is visible to everyone).

GitHub Pages: the free demo

.github/workflows/pages.yml runs on every push to main:

on: { push: { branches: [main] } }
jobs:
  deploy:
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
      - run: npm ci
      - run: npm run build:site          # tsc + copy public/ and dist/client/ into site/
      - uses: actions/upload-pages-artifact@v3   (path: site)
      - uses: actions/deploy-pages@v4

One-time setup: repository Settings → Pages → Source: GitHub Actions. Without that, the deploy step fails with "Ensure GitHub Pages has been enabled" (exactly what happened the first time). Result: https://shouryasengar.github.io/jira-bug-dashboard/. Because there is no server there, the page runs in demo mode.

Pushing a feature branch does not deployThe workflow only runs for main, so pushing feature/cloudflare-web-edition changes nothing on the live demo. The Cloud edition is deployed separately with Wrangler.

Merging the feature branch (when ready)

git checkout main
git merge --no-ff feature/cloudflare-web-edition
npm install && npm run build && (run the local tests)
git push origin main             # also redeploys the Pages demo

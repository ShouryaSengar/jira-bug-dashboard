Every Cloudflare feature the Cloud edition uses, with the exact configuration and commands, and how they fit together in wrangler.jsonc.

Bindings: how code reaches resources

A Worker cannot "connect" to a database with a password. Instead you declare a binding in the configuration, and Cloudflare injects an object into env:

"d1_databases": [{ "binding": "DB", "database_name": "jbd-cloud", "database_id": "9e6d337d-…" }]
// in code:
const row = await env.DB.prepare('SELECT name FROM users WHERE id = ?').bind(id).first();

No credentials in code, and the Worker can only reach what is bound to it.

D1: the database

  • SQLite inside: standard SQL, tables, indexes, foreign keys, transactions.
  • One primary location (this one: APAC), chosen near the first request. Reads and writes go there.
  • API: prepare(sql).bind(...).first() / .all() / .run(), and env.DB.batch([...]) for several statements as one transaction and one subrequest.
  • Always bind parameters (?) instead of building SQL strings from input: that prevents SQL injection.
  • Local copy: --local uses a SQLite file under .wrangler/state; --remote is the real one.
  • Time travel: D1 can restore a database to a point in the past (7 days on Free).
npx wrangler d1 create jbd-cloud                                    # create (prints the id)
npx wrangler d1 migrations apply DB --remote --env production       # apply schema files
npx wrangler d1 execute DB --remote --env production --command "SELECT COUNT(*) FROM users"
npx wrangler d1 export jbd-cloud --remote --output backup.sql       # backup

Workers Static Assets

"assets": {
  "directory": "./dist-assets",            // what to upload
  "binding": "ASSETS",                     // env.ASSETS.fetch(request) serves a file
  "run_worker_first": ["/api/*", "/auth/*"] // only these paths run your code
}
  • Requests that match a file are served directly, free and unlimited.
  • HTML handling: /privacy.html redirects to the cleaner /privacy; /learn/ serves /learn/index.html.
  • A _headers file in the directory adds response headers per path (this app's CSP, HSTS, no framing).
  • Assets are uploaded with each deploy; unchanged files are skipped.

Cron Triggers

"triggers": { "crons": ["* * * * *"] }    // minute hour day-of-month month day-of-week
ExpressionMeaning
* * * * *every minute
*/5 * * * *every 5 minutes
0 9 * * 1-509:00 UTC on weekdays
37 * * * *minute 37 of every hour
  • Times are UTC. The Worker's scheduled() receives event.scheduledTime.
  • One trigger can serve all users: this app uses one every-minute trigger and decides inside which users are due (their slot), plus hourly jobs at minutes 13 and 37.
  • Local testing: wrangler dev --test-scheduled, then curl "http://localhost:8787/__scheduled?cron=*+*+*+*+*".

Both appear in code as env.NAME. A name cannot be both a variable and a secret. Locally, secrets come from cloud/.dev.vars (git-ignored).

Setting secrets without leaking themwrangler secret put NAME prompts and hides your input. For generated values, pipe them in: the app's set-prod-secrets.mjs generates keys in memory and writes them to Wrangler's standard input, so they never appear on screen, in a file, or in shell history.

Environments

One configuration file, several copies of the app:

"env": {
  "dev":        { "name": "jira-bug-dashboard-cloud-dev", "vars": { … mocks … }, "d1_databases": [ … ], "triggers": { … } },
  "production": { "name": "jira-bug-dashboard-cloud",     "vars": { … real … },  "d1_databases": [ … ], "triggers": { … } }
}
  • Pick one with --env dev or --env production on every command.
  • Bindings, vars and triggers are not inherited from the top level: repeat them in each environment.
  • Secrets are per environment too.

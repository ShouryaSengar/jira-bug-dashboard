Playbook: deploy any new app on Cloudflare

A reusable recipe for your next project, distilled from building this one. It takes you from an empty folder to a live app with a database, a schedule, secrets, two environments, tests, and a rollback plan.

⏱ 15 min readGuide 42 of 47

0. Decide the shape

Your app is…Use
static only (HTML/CSS/JS)a Worker with only assets (or Cloudflare Pages); no code needed
static + an APIone Worker with assets + run_worker_first: ["/api/*"] (this app's shape)
needs to store dataD1 for relational data; KV for simple key-value caches; R2 for files
does work on a scheduleCron Triggers (max 5 per account on Free; one trigger can serve many jobs)
needs long-lived connections or strong per-object coordinationDurable Objects
background jobs with retriesQueues

1. Create the project

mkdir my-app && cd my-app
npm init -y
npm install -D wrangler typescript @cloudflare/workers-types
mkdir -p src public migrations

package.json: add "type": "module". tsconfig.json:

{ "compilerOptions": { "target": "ES2022", "module": "ES2022", "moduleResolution": "Bundler",
    "lib": ["ES2023"], "types": ["@cloudflare/workers-types"], "strict": true, "noEmit": true },
  "include": ["src"] }

2. Write the Worker

// src/index.ts
export interface Env { DB: D1Database; ASSETS: Fetcher; APP_ORIGIN: string; API_SECRET: string }

export default {
  async fetch(req: Request, env: Env): Promise<Response> {
    const url = new URL(req.url);
    if (url.pathname === '/api/hello') {
      const row = await env.DB.prepare('SELECT COUNT(*) AS n FROM visits').first<{ n: number }>();
      return Response.json({ hello: 'world', visits: row?.n ?? 0 });
    }
    return env.ASSETS.fetch(req);
  },
  async scheduled(_c: ScheduledController, env: Env, ctx: ExecutionContext) {
    ctx.waitUntil(env.DB.prepare('INSERT INTO visits (at) VALUES (?)').bind(Date.now()).run());
  },
} satisfies ExportedHandler<Env>;

public/index.html: any page. migrations/0001_init.sql:

CREATE TABLE visits (id INTEGER PRIMARY KEY AUTOINCREMENT, at INTEGER NOT NULL);

3. Configure: wrangler.jsonc

{
  "$schema": "node_modules/wrangler/config-schema.json",
  "name": "my-app",
  "main": "src/index.ts",
  "compatibility_date": "2026-11-01",
  "assets": { "directory": "./public", "binding": "ASSETS", "run_worker_first": ["/api/*"] },
  "observability": { "enabled": true },
  "env": {
    "dev": {
      "name": "my-app-dev",
      "vars": { "APP_ORIGIN": "http://localhost:8787" },
      "d1_databases": [{ "binding": "DB", "database_name": "my-app-dev", "database_id": "00000000-0000-0000-0000-000000000000", "migrations_dir": "migrations" }],
      "triggers": { "crons": ["*/5 * * * *"] }
    },
    "production": {
      "name": "my-app",
      "vars": { "APP_ORIGIN": "https://my-app.<subdomain>.workers.dev" },
      "d1_databases": [{ "binding": "DB", "database_name": "my-app", "database_id": "<from d1 create>", "migrations_dir": "migrations" }],
      "triggers": { "crons": ["*/5 * * * *"] }
    }
  }
}
Not inheritedBindings, vars and triggers must be repeated inside each environment. Secrets are per environment too.

4. Run locally

echo "API_SECRET=dev-only-value" > .dev.vars         # local secrets; add .dev.vars to .gitignore!
npx wrangler d1 migrations apply DB --local --env dev
npx wrangler dev --env dev --test-scheduled
curl http://localhost:8787/api/hello
curl "http://localhost:8787/__scheduled?cron=*/5+*+*+*+*"

5. Go live

npx wrangler login
npx wrangler d1 create my-app                        # copy the id into wrangler.jsonc
npx wrangler d1 migrations apply DB --remote --env production
npx wrangler secret put API_SECRET --env production  # prompts, hidden
npx wrangler deploy --env production
npx wrangler tail --env production                   # watch it

6. Make it production-grade

Security

  • Secrets only via wrangler secret put; never in wrangler.jsonc or Git.
  • Bound SQL parameters (?) always.
  • Security headers on HTML (public/_headers) and API responses (CSP, HSTS, nosniff, frame denial).
  • If you have sign-in: HttpOnly Secure SameSite cookies, CSRF checks on state changes, never trust ids from the client.
  • If you call user-supplied URLs: allow-list hosts (SSRF).
  • Fail closed when configuration is missing (this app answers 503 "not configured").

Limits (Free)

  • Count subrequests (50 per run, D1 included); batch D1 statements with env.DB.batch().
  • Keep CPU low (10 ms): small payloads, request only needed fields, cap work per cron run, defer the rest.
  • Write to D1 only when something changed (100,000 rows/day).
  • Make scheduled work idempotent and resumable: it can be cut off at any point.

Operations

  • Migrations: numbered, additive, never edited after running in production.
  • Logs: console.log structured JSON summaries; never log secrets or personal data.
  • Backups: wrangler d1 export … --remote before risky changes; D1 time travel exists.
  • Rollback: wrangler rollback (code only: database changes are not rolled back, another reason to keep migrations additive).

Tests

  • A mock for every external service (start it on a local port, point a vars URL at it in dev).
  • End-to-end tests against wrangler dev using plain fetch with a cookie jar.
  • Unit tests by bundling modules with esbuild (ships with Wrangler) and importing them in Node.

7. Custom domain (optional)

Add your domain to Cloudflare (it becomes a zone), then in the Worker's settings add a Custom Domain (or a routes entry in wrangler.jsonc). Update APP_ORIGIN and any OAuth callback URLs. With a zone you can also add WAF and rate-limiting rules in front of the Worker.

Template checklist

  • ☐ wrangler.jsonc with dev and production
  • ☐ .gitignore: node_modules, .wrangler, .dev.vars, build output
  • ☐ migrations folder, first migration
  • ☐ _headers with CSP
  • ☐ secrets listed in a README (names, not values)
  • ☐ npm run dev, npm run deploy, npm test scripts
  • ☐ a mock + an end-to-end test
  • ☐ wrangler tail checked after the first deploy

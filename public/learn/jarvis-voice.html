JARVIS: speech and notifications

How events become words and notifications: the templates, the grouping rules, quiet hours, voice selection, the browser's rules, and how several open tabs avoid talking over each other.

⏱ 10 min readGuide 18 of 47

From events to announcements: plan()

plan(batch, prefs, now) in src/client/jarvis-core.ts is a pure function: given a batch of events and the user's preferences, it returns what to show and say. The browser and the Worker (for push text) both use it.

  1. Silence checks: during quiet hours → nothing. Drop own actions and disabled event types. In "important only" mode keep only high-importance events plus resolutions.
  2. Collapse repeats: same bug + same type → one item with a count ("ABC-1: 3 new comments").
  3. Sort by importance, then time.
  4. Decide speech: up to 2 items are spoken one by one; 3 or more become one briefing (in digest mode already from 2). Low-importance items are never spoken.
  5. Decide notifications: at most 2 individual notifications plus one summary ("4 more updates on your bugs") when there are more than 3 items.
// a burst of 6 updates becomes:
"ABC-1: new comment · Bob"            (notification)
"ABC-2: priority raised to Highest"   (notification)
"4 more updates on your bugs"         (notification)
"Sir, a quick briefing. 6 updates across 4 bugs: 1 new assignment, 3 new comments, … Most notable: A B C 7, newly assigned."  (speech)

The templates

Each event type has several hand-written variations; the same one is never used twice in a row (pickVariant remembers the last choice). Placeholders are filled from the event:

EventExample
assigned"Good evening, sir. A new bug has landed on your desk. A B C 123, Login button does not respond, has just been assigned to you. Shall we take a look?"
status"Sir, a quick update. A B C 123 has moved to In Progress."
comment"Bob Builder has weighed in on A B C 123, sir."
priority up"Attention, sir. The priority of A B C 123 has just been escalated to Highest."
reopened"Well, sir. A B C 123 is back from the dead. The issue has been reopened."
resolved"Excellent work, sir. A B C 123 has been marked as resolved. One less problem on the board."
closed"Mission accomplished, sir. A B C 123 is officially closed."
  • Spoken keys: ABC-123 becomes "A B C 123" so the voice spells the project instead of reading "abc" as a word.
  • Spoken summaries: links become "a link", markup is stripped, long summaries are cut at a word boundary (70 characters).
  • Address: "sir", "ma'am", "boss" or nothing, chosen in settings; the greeting follows the time of day.
  • "While you were away": when the app opens and finds unread events newer than the last announced id, it gives one briefing instead of replaying each.
No AI involvedAll wording comes from fixed templates. There are no network calls, no model, no cost, and the output is predictable and testable (33 tests cover the rules).

The speaker (speech.ts)

  • One voice at a time: a queue of up to 5 lines; each waits for the previous one's end event, plus 350 ms of pause.
  • Stale lines are dropped: anything waiting more than 2 minutes (except test announcements).
  • Safety timer: some browsers never fire end; a timeout based on text length moves on anyway.
  • Voice choice: your pick in settings, otherwise the best available English voice in this order: Microsoft Andrew (Natural), other Microsoft Natural voices, Daniel (macOS British), Google UK English Male, and other fallbacks.
  • The "click first" rule: Chrome and Edge refuse to speak until the user has interacted with the page once. Lines wait until the first click or key press; the header shows "Click anywhere to enable voice".

Notifications

  • In-page (all editions): new Notification(title, {body, tag}) while the tab is open, if permission is granted. Clicking opens the bug's detail. High-importance ones stay until dismissed.
  • Push (cloud): the service worker shows them, even with the browser closed. When a push already showed a notification, the page does not show a second one for the same events.
  • System (local): macOS/Linux notifications from the Node server when no tab is connected.
  • Permission is only requested from a click (browsers require a user gesture).

Several tabs

If you have three dashboard tabs open, only one should speak. Each tab writes a heartbeat to localStorage every 5 seconds, saying whether it is allowed to speak. When events arrive:

  1. A tab that cannot speak yet steps aside if another able tab is alive.
  2. Otherwise it tries to claim the batch (highest event id) inside a Web Lock, so two tabs cannot claim the same batch at the same moment.
  3. Claims expire after 20 seconds; tabs remove their heartbeat when closed.

Server-side rules for push (cloud)

When the browser is closed, the browser's preferences are not available, so the page copies the relevant ones to the server (POST /api/jarvis/notify): enabled event types, frequency, quiet hours and your time zone. The Worker applies them with pushPlan(), computing "now" in your time zone with Intl.DateTimeFormat. Events silenced by quiet hours are still recorded as unread.

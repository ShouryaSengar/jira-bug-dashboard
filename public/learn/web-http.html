HTTP, cookies, CORS and same-origin

The browser's rules of the road. Understanding them explains why this app needs a server, how sign-in stays secure, and why some attacks simply cannot work.

⏱ 12 min readGuide 33 of 47

HTTP: the conversation

Every interaction is a request and a response:

GET /api/mine HTTP/1.1                         ← method + path
Host: jira-bug-dashboard-cloud.shouryacode2021.workers.dev
Cookie: __Host-jbd_sid=Qm9i…                   ← headers
Accept: application/json

HTTP/1.1 200 OK                                ← status
Content-Type: application/json; charset=utf-8
Cache-Control: no-store
X-Content-Type-Options: nosniff

{"me":{"name":"Shourya"},"bugs":[…]}            ← body
MethodsMeaning
GETread something; must not change anything
POSTdo something / send data
DELETEremove something
Status codesMeaning
200, 202, 204OK / accepted / OK with no body
302, 307go somewhere else (redirect)
400, 401, 403, 404, 409, 413, 429your fault: bad input, not signed in, forbidden, not found, conflict, too large, too many
500, 502, 503server's fault: error, upstream error, unavailable

HTTPS is the same conversation inside TLS encryption, so nobody on the network can read or change it.

Origins

An origin is scheme + host + port. These are three different origins:

https://jira-bug-dashboard-cloud.shouryacode2021.workers.dev
https://axismaxlife.atlassian.net
http://localhost:4545

The browser treats each origin as a separate world.

Same-origin policy and CORS

Explained simplyEach website is a house. A script in one house can send letters to other houses, but it is not allowed to open the replies addressed back from another house, unless that house wrote "you may read this" on the envelope. That note is CORS.

When a page on origin A calls fetch() to origin B, the browser sends it (sometimes after asking permission first with an OPTIONS "preflight"), and only lets the page read the response if B answers with headers like Access-Control-Allow-Origin: A.

Jira Cloud does not allow this for API requests carrying credentials. So a page on workers.dev or github.io can never read Jira directly. That is the root reason every edition with real data has a server, which, being a server and not a browser, is not subject to CORS.

The app's own API never sends CORS headers either. That is deliberate: no other website can read its responses with your cookies.

Cookies

A server sets a cookie with a response header; the browser stores it and sends it back on every request to that site:

Set-Cookie: __Host-jbd_sid=Qm9i…; Path=/; Max-Age=2592000; HttpOnly; Secure; SameSite=Lax
AttributeEffectWhy the app uses it
__Host- prefixbrowser only accepts it with Secure, Path=/ and no Domainsub-domains cannot plant or overwrite it
HttpOnlyJavaScript cannot read itan injected script cannot steal the session
Secureonly sent over HTTPS (and localhost)never travels unencrypted
SameSite=Laxnot sent on cross-site sub-requests (images, fetch, forms posted from other sites); sent on top-level linksblocks most CSRF; still works when Atlassian redirects you back
Max-Agelifetime in seconds30 days for the session, 10 minutes for the OAuth state

CSRF in one picture

Cross-site request forgery: a malicious page makes your browser send a request to a site where you are signed in, and the browser helpfully attaches your cookie. Defences used here:

  1. SameSite=Lax cookies are not sent on cross-site POSTs.
  2. Every state-changing request must carry X-JBD: 1. A cross-site page cannot add custom headers without a CORS preflight, which the API never approves.
  3. The Origin header must equal the app's origin; Sec-Fetch-Site must not be cross-site.

Other headers the app sends

HeaderPurpose
Content-Security-Policyonly run scripts from our own origin; no inline scripts; no framing; connect only to ourselves
Strict-Transport-Securitybrowser must always use HTTPS for this site
X-Frame-Options: DENYcannot be embedded in someone else's page (clickjacking)
X-Content-Type-Options: nosniffbrowser must trust the declared content type
Referrer-Policy: no-referrerdo not leak our URLs to other sites
Cache-Control: no-storeAPI data is never stored by caches

localStorage

A per-origin key-value store in the browser that survives restarts. Any script on the page can read it, so it is only for non-secret things: preferences, filters, caches, your Learn progress. Tokens are never stored there.

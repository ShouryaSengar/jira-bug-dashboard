Threat model and defences

Who might attack the app, what they would want, how they might try, and the specific defence for each. Every defence listed is implemented and most are covered by automated tests.

What is worth protecting

  1. Jira access (OAuth tokens, API tokens): the crown jewels; they unlock company data.
  2. Sessions: a stolen session acts as the user in the app.
  3. Personal data: names, emails, bug summaries in history.
  4. Availability: staying inside the free tier for everyone.

Threats and defences

Token theft

  • Tokens never reach the browser (the server calls Jira).
  • Encrypted at rest (AES-256-GCM), key held separately as a Worker secret; bound to the user id.
  • Never logged; responses never include them.
  • Read-only scopes; resource-level grants.

Session hijacking

  • 32 random bytes per session (unguessable); only its SHA-256 hash stored.
  • Cookie __Host-, HttpOnly, Secure, SameSite=Lax; HSTS forces HTTPS.
  • 30-day absolute and 7-day idle expiry; disconnect signs out everywhere.

CSRF (cross-site request forgery)

Custom X-JBD header + Origin check + Sec-Fetch-Site check + SameSite cookies on every state change. Tests send requests without the header, with a foreign Origin and with Sec-Fetch-Site: cross-site: all refused.

Login CSRF and OAuth code theft

Random state bound to an HttpOnly cookie, compared in constant time; codes are single-use and need the client secret; Atlassian only redirects to the registered callback. Tests: forged state, missing cookie, code replay.

IDOR (seeing someone else's data)

No endpoint accepts a user id. Every query includes user_id = <session user>. Client-supplied ids (event ids, device ids, site ids) are combined with that filter. Tests: a second user tries to read, mark read, clear, unsubscribe and switch to another user's data: no effect.

XSS (cross-site scripting)

  • Every dynamic value is HTML-escaped (esc()); links pass through safeUrl() (http/https only).
  • Strict CSP: script-src 'self', no inline scripts, frame-ancestors 'none'.
  • Text from Jira is rendered as text, never as HTML.

SSRF (making the server call internal addresses)

The only user-supplied URLs the server calls are push endpoints: HTTPS only, no credentials in the URL, host must be an allow-listed push service. Tests try 169.254.169.254, look-alike hosts and HTTP.

Injection (SQL, JQL, shell)

  • SQL: always bound parameters (?), never string-built from input.
  • JQL: issue keys validated by regex; issue types quoted and stripped of quotes/backslashes.
  • Shell (Local edition notifications): execFile with an argument array, never a shell string.

Abuse and denial of service

  • Sign-in limited per IP (D1, 30 per 10 minutes); per-user limits on API, "check now" and test pushes; request bodies capped at 16 KB.
  • Monitor work bounded per run; back-off on errors.
  • Cloudflare's network absorbs volumetric attacks in front of the Worker.

Secrets in the repository

.dev.vars and build output are git-ignored; production secrets are set with wrangler secret put or piped in by script; the contact email is a secret so it is not published; staged changes are scanned for key-like strings before commits.

Local edition specifics

Binds to 127.0.0.1; Host header allow-list (DNS rebinding); credentials file mode 0600 outside the project.

Residual risks (honest list)

  • The operator of a Cloud instance controls the Worker secrets and could, in principle, decrypt users' tokens. Users must trust the operator; teams that do not can self-host.
  • The in-memory rate limiter is per isolate; a determined attacker spreading requests can exceed it (Cloudflare WAF rules on a custom domain help).
  • Browser extensions with full page access can read anything the page shows (not tokens).
  • Dependencies: deliberately few (TypeScript and Wrangler at build time only), but not zero.

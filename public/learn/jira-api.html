How Jira's REST API works

The parts of Jira Cloud's REST API this app uses: issues and fields, JQL search, pagination, changelogs, comments, rich text, statuses and priorities, and rate limits.

⏱ 12 min readGuide 25 of 47

Issues and fields

Everything in Jira is an issue (a bug, a story, an epic) identified by a key like ABC-123 (project ABC, number 123). An issue is a bag of fields:

GET /rest/api/3/issue/ABC-123?fields=summary,status,priority,assignee,updated
{
  "key": "ABC-123",
  "fields": {
    "summary": "Login fails on Safari",
    "status":   { "id": "3", "name": "In Progress", "statusCategory": { "key": "indeterminate" } },
    "priority": { "name": "High" },
    "assignee": { "accountId": "5b10…", "displayName": "Ava Chen" },
    "updated":  "2026-11-18T10:58:09.000+0530",
    "customfield_12039": { "value": "2 - Major" }
  }
}
  • System fields have names (summary, status…). Custom fields are added by admins and have ids like customfield_12039. "Severity" is a custom field, so the app finds its id by name (settings: Severity field names or IDs).
  • Always ask only for the fields you need (fields=…); full issues are large.
  • People are identified by an opaque accountId, not by email (privacy rules).

JQL: searching

JQL looks like SQL for issues. The searches this app runs:

PurposeJQL
Epics view(issue in linkedIssues("ABC-1") OR parent = "ABC-1") AND issuetype in ("Bug") ORDER BY created DESC
For Youassignee = currentUser() AND issuetype in ("Bug") AND (statusCategory != Done OR updated >= -90d) ORDER BY updated DESC
Recently assignedassignee = currentUser() AND assignee CHANGED TO currentUser() AFTER -7d
JARVIS incrementalissuetype in ("Bug") AND ((assignee = currentUser() AND updated >= -12m) OR assignee CHANGED FROM currentUser() AFTER -12m) ORDER BY updated ASC
  • currentUser() means "whoever owns the token", so the same JQL works for every user.
  • -12m, -90d are relative dates. Absolute dates ("2026-11-18 10:00") are interpreted in the user's Jira time zone, a classic source of bugs; relative ones avoid it.
  • CHANGED FROM … AFTER searches field history, which is how the app spots bugs taken away from you.
  • Values from settings (issue types) are quoted and stripped of quotes/backslashes before being put into JQL, so a setting cannot change the query's meaning.

Pagination

The search endpoint returns at most 100 issues per page:

POST /rest/api/3/search/jql
{ "jql": "…", "fields": ["summary","status",…], "maxResults": 100, "nextPageToken": "…" }

→ { "issues": [ … ], "isLast": false, "nextPageToken": "CAEaAggD" }

searchAll() keeps asking with the returned nextPageToken until isLast is true or a cap is reached (1000 locally, 300 for For You in the cloud, 500 for the monitor's full list).

Changelog: the issue's history

GET /rest/api/3/issue/ABC-1/changelog?startAt=0&maxResults=100
{ "total": 13, "isLast": true, "values": [
  { "id": "10234", "author": { "accountId": "…", "displayName": "Bob" }, "created": "2026-11-18T12:16:39.000+0530",
    "items": [ { "field": "status", "fieldId": "status", "from": "10001", "fromString": "Needs Information",
                 "to": "11330", "toString": "Bug Fix" } ] }
] }
  • Entries are oldest first. For long histories the app jumps to the last page (startAt = total − 100).
  • For status, from/to are status ids; for assignee, account ids. fromString/toString are display names.
  • id + fieldId together identify one change forever: the basis of JARVIS's de-duplication.

Comments and rich text

GET /rest/api/3/issue/ABC-1/comment?orderBy=-created&maxResults=15

Comment bodies and descriptions are in Atlassian Document Format (ADF): a JSON tree of paragraphs, text, mentions, lists, code blocks, tables and media. adfToText() walks the tree and produces readable text, for example a bullet list becomes lines starting with "•", a mention becomes "@Name", an attachment becomes "[attachment]".

Statuses, categories and priorities

  • Every site invents its own statuses ("Bug Fix", "Retest", "Needs Information"). Each belongs to one of three categories: new, indeterminate, done. The app reasons with categories: done → not done = reopened.
  • GET /rest/api/3/status/{id} gives one status with its category (the cloud looks up unknown ones lazily; one real site has 662 statuses, too many to load every time).
  • GET /rest/api/3/priority lists priorities in the admin's order, which is not always urgency (see the Blocker story in JARVIS engine).

Errors and rate limits

StatusMeaningApp behaviour
400bad JQL or parametersmessage from errorMessages shown
401token invalid / expiredcloud: refresh once, then reauth; local: "check email and API token"
403 / 404no permission / does not exist (Jira often answers 404 for both, to avoid leaking existence)shown; monitor ignores that issue
429rate limited; Retry-After says how long to waitback off at least that long

Jira Cloud's rate limits are per user and app, based on cost over time. The monitor's incremental design (one small search per user per interval) keeps far below them.

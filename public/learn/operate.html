Operating in production

Keeping the live Cloud edition healthy: what to watch, how to read logs, how to roll back, back up, rotate keys and handle incidents.

⏱ 10 min readGuide 43 of 47

Daily glance (2 minutes)

  • Dashboard → Workers & Pages → jira-bug-dashboard-cloud → Metrics: requests, errors, CPU time (median and p99 well under 10 ms).
  • Dashboard → D1 → jbd-cloud → Metrics: rows read/written per day against 5M/100k.
  • Open the app; the JARVIS dot should be green.

Logs

cd cloud
npx wrangler tail --env production --format pretty           # everything
npx wrangler tail --env production --status error            # only failures

What normal looks like:

"* * * * *" @ …  - Ok
  (log) {"tick":"…","due":2,"checked":2,"events":1,"deferred":0,"subrequests":9}
GET https://…/api/mine - Ok
POST https://…/api/jarvis/notify - Ok
FieldWatch for
deferredoften > 0 → more users than capacity; raise interval or upgrade
subrequestsclose to 45 regularly → many busy users per minute
monitor: user check failedrepeated for one user → see monitor_state.last_error
personal data reporting failednon-200/204 from Atlassian → check the token / Atlassian status

Cloudflare redacts OAuth code and state in logged URLs. The app never logs tokens or Jira content.

Useful read-only queries

Q="npx wrangler d1 execute DB --remote --env production --command"
$Q "SELECT COUNT(*) users FROM users"
$Q "SELECT status, COUNT(*) FROM oauth_grants GROUP BY status"
$Q "SELECT user_id, failures, last_error FROM monitor_state WHERE failures > 0"
$Q "SELECT COUNT(*) pending FROM events WHERE pushed = 0"
$Q "SELECT COUNT(*) devices FROM push_subscriptions"
$Q "SELECT * FROM app_meta"

Deploying changes safely

  1. Run the test suites locally (How this app is tested).
  2. npm run deploy:dry: bundle, size, bindings.
  3. New migration? Make it additive (new tables/columns with defaults).
  4. npm run deploy.
  5. Watch wrangler tail for a few minutes and open the app.

Rolling back

npx wrangler deployments list --env production
npx wrangler rollback --env production                # previous version
npx wrangler rollback <version-id> --env production   # a specific one

A rollback changes code only. Database migrations are not undone, which is why migrations must stay compatible with the previous code.

Backups

npx wrangler d1 export jbd-cloud --remote --output backup-$(date +%F).sql
npx wrangler d1 time-travel info jbd-cloud
npx wrangler d1 time-travel restore jbd-cloud --timestamp 2026-11-18T19:00:00Z   # 7 days on Free
Backups contain personal dataAn export contains names, emails and encrypted tokens. Store it encrypted, delete it when no longer needed, and never commit it.

Incident playbook

SituationFirst steps
Everyone sees errorswrangler tail --status error; if it started after a deploy, roll back
Error 1027 / 429 everywheredaily free limit reached; wait for 00:00 UTC; find the cause in metrics
CPU errors (1102)lower MONITOR_MAX_USERS_PER_RUN; check for users with huge bug lists
Suspected secret leakrotate the secret now (table above); for the client secret, regenerate at Atlassian; review logs
A user asks to be forgottenthey can delete their account in Settings; or delete by account id with the same statements privacy.ts uses
Atlassian revoked the appevery grant fails with invalid_grant; users see "Reconnect"; check the developer console

Turning it off

npx wrangler delete --env production      # Worker + cron gone; the URL stops working
npx wrangler d1 delete jbd-cloud          # data gone (irreversible; export first if needed)

Also set the Atlassian app's distribution to "Not sharing" or delete it in the developer console.

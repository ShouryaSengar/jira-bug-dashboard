The background check (cron)

Every minute Cloudflare wakes the Worker. Here is everything that happens in that one run, why it is safe to stop half way, and how it stays inside 10 ms of CPU and 50 subrequests.

⏱ 12 min readGuide 22 of 47
Explained simplyA night guard does a round every minute. There are many rooms (users), but the guard only has time for about a dozen per round, so each room has its own minute on a rota. In each room the guard asks one quick question ("anything new since my last visit?"). Only if the answer is yes does the guard look closer and write it in the logbook. If the round runs out of time, the guard notes the unfinished rooms and starts with them next round.

The run

1. Who is due

Each user has a random slot (0–59) and an interval (default 5 minutes). A user is due when (minute − slot) mod interval = 0, or when they were deferred last minute. One SQL query returns, for every due user, everything the check needs: account id, site, settings, the encrypted grant, and the checkpoint (snapshot, seen ids, status categories). See the query in Database design.

Users in back-off (after errors) and users with a revoked grant are not selected.

2. Checking a user

Covered in detail in JARVIS: how changes are detected. In short: refresh the token if needed, run one incremental search, read history only for bugs that changed, classify, commit in one batch.

3. Limits and how they are respected

Limit (Workers Free)Mechanism
50 subrequests per run (D1 included)Budget(45); a user is started only if 6 are left; inside a user, a changed bug is processed only if 3–4 are left
10 ms CPU per runat most 12 users per run (MONITOR_MAX_USERS_PER_RUN); idle checks cost ~0.4 ms
100,000 D1 writes per dayidle checks write nothing; a heartbeat every 20 minutes

When the budget runs out, the remaining users get deferred = 1 (one batched write) and go first next minute. A user cut short keeps their old checked_at, so the next incremental window still covers the unprocessed bugs: nothing is lost.

4. Errors

  • Jira rate limit (429): back off at least the Retry-After seconds.
  • Other failures: back off interval × 2^failures, at most 60 minutes; the error message is stored (no tokens, no Jira content) and shown in the JARVIS panel.
  • Revoked access: the grant is marked revoked; the user is skipped until they reconnect.

5. After the users

  • Retry pushes: events still marked pushed = 0 (the push service was down, or the budget ran out) are retried; after 6 hours they are marked "gave up". The events are still in the history.
  • Minute :37 of each hour: personal-data report for accounts that are due.
  • Minute :13 of each hour: delete expired sessions and rate-limit rows, history older than 30 days, and accounts whose Jira access ended more than 30 days ago.

What it looks like in the logs

$ npx wrangler tail --env production
"* * * * *" @ 19/11/2026, 12:56:44 am - Ok
  (log) {"tick":"2026-11-18T18:56:44.066Z","due":1,"checked":1,"events":0,"deferred":0,"subrequests":5}

due: users selected; checked: processed; events: new events; subrequests: budget used. An idle minute with nobody due uses 2 (the due-users query and the pending-push sweep).

Capacity

12 users per minute × 5-minute interval ≈ 60 users with no delay. With more users, the effective interval stretches (deferred users first); nothing is dropped. The Local edition has no such limits because it runs on your computer for one user. Numbers and the paid-plan option: The free tier and capacity maths.

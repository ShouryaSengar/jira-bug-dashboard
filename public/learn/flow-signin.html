Signing in with Atlassian

The OAuth 2.0 authorization-code flow ("3LO") from start to finish. This is the most important security flow in the app, so every hop is explained, including what an attacker might try at each step.

⏱ 12 min readGuide 20 of 47
Explained simply: the hotel key card

You want a cleaner (the app) to enter your hotel room (your Jira) to tidy one thing. You do not give the cleaner your passport (your password). Instead:

  1. The cleaner sends you to the reception desk (Atlassian) with a note saying who they are.
  2. Reception checks your ID and asks you: "This cleaner wants to look at your room, read-only. OK?"
  3. You say yes. Reception gives you a one-time ticket to hand back to the cleaner.
  4. The cleaner takes the ticket to reception privately, together with the cleaner's own badge (the client secret), and receives a key card (access token) that works for an hour, plus a refill voucher (refresh token).

You never told the cleaner your password, you can cancel the key card at reception any time, and the card only opens what you agreed to.

The sequence

Each hop explained

1–3. Starting the flow (startLogin)

  • A per-IP counter in D1 allows 30 sign-in attempts per 10 minutes (the IP is stored only as a hash, and only for that window).
  • A random state (24 random bytes) is generated and stored in the cookie __Host-jbd_oauth (HttpOnly, Secure, SameSite=Lax, 10 minutes).
  • The redirect URL contains: audience=api.atlassian.com, the public client_id, scope=read:jira-work read:jira-user read:me offline_access, redirect_uri=…/auth/callback, the state, response_type=code, prompt=consent.

4–6. At Atlassian

Atlassian authenticates you (password, SSO, two-factor: whatever your organisation uses; the app never sees it), shows the requested read-only permissions, and with a resource-level grant asks which site to share. Then it redirects back with a short-lived, one-time code and the same state.

7–8. Back at the Worker (finishLogin)

  • The state in the URL must equal the one in the cookie (compared in constant time). Otherwise → /?auth=state.
  • If you clicked Cancel → /?auth=denied.

9–10. The code exchange

Server to server, the Worker posts the code, the client_secret (a Worker secret) and the same redirect URI to /oauth/token. It receives an access token (valid about an hour), a refresh token (because of offline_access) and the scopes actually granted. If a required scope is missing → /?auth=scopes.

11–12. Who and where

GET api.atlassian.com/me gives your account id, name, email and picture. GET /oauth/token/accessible-resources gives the sites this token can reach, each with a cloudId. Sites without read:jira-work are ignored; none left → /?auth=nosite.

13–14. Saving, atomically

One D1 batch: upsert the user (by Atlassian account id), store the grant encrypted with AES-256-GCM (additional data grant:<userId>), replace the site list, create settings with a random monitoring slot, and insert a session whose id is the SHA-256 of a fresh 32-byte random cookie value. Then the browser gets __Host-jbd_sid (30 days) and is sent to For You.

What an attacker might try

AttackWhy it fails
Send you a link to /auth/callback with their code (login CSRF: you end up signed in to their Jira)Your browser has no matching state cookie (or a different one) → refused
Steal a code from logs or history and reuse itCodes are single-use and need the client secret; replay returns /?auth=exchange (tested)
Change redirect_uri to their siteAtlassian only redirects to the callback URL registered in the developer console
Read the tokens from the pageThey never reach the browser
Read the tokens from a database leakEncrypted; the key is a separate Worker secret
Hammer the sign-in endpointPer-IP limit in D1

Signing out and reconnecting

  • Sign out deletes this session row and the cookie.
  • Disconnect Jira deletes the grant, sites, monitor state, push devices and all sessions.
  • Reconnect (after revocation or expiry) is the same flow; the existing user row is reused, so history and settings remain.

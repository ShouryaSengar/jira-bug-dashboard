JARVIS: how changes are detected

The algorithm that turns "something happened in Jira" into exactly one well-labelled event, never zero, never two. Shared by both editions.

The hard part

Jira does not tell a private app "Bob just commented on ABC-1". The app has to look and work it out. Naive approaches fail:

  • Compare updated times only: you know that something changed, not what. A label edit and a reopen look the same.
  • Announce the whole history on first run: users get flooded with years of old changes.
  • Remember "last check time" only: overlapping windows, clock differences and retries produce duplicates.

JARVIS combines four ideas: a baseline, a snapshot, the changelog, and a seen set.

The four ideas

IdeaWhat it isWhat it prevents
BaselineThe first check only records what existsannouncing old history
SnapshotFor each bug I hold: its updated time, summary, projectre-reading bugs that did not change
Changelog + commentsJira's own record of every field change and comment, with author and timeguessing what changed
Seen setStable ids of every changelog item and comment already processed (ABC-1:h10234:status, ABC-1:c55012)duplicates, across restarts and overlaps

One check, step by step (Cloud edition)

  1. Get a token (refresh it if it expires within 2 minutes).
  2. Choose the kind of check. First time, or 6 hours since the last full comparison, or checkpoint older than 7 days → a full list. Otherwise → incremental.
  3. Incremental search. The window N = minutes since the last fully processed check + 3, at least 10, at most 7 days. Results are ordered oldest first, so if the run is cut short the oldest are handled first.
  4. For each result:
    • still mine and updated equals the snapshot → already handled in an earlier, overlapping window → skip;
    • not mine any more → classifyAway using the assignee in the result itself (no extra call), drop from snapshot;
    • mine but not in the snapshot → read the changelog → classifyNew finds the newest "assignee → me" entry, so the event can say who assigned it;
    • mine and changed → read changelog + 15 newest comments → classifyChanges for entries newer than the snapshot's updated (minus 1.5 s of slack).
  5. Learn statuses lazily: unknown status ids in the changelog are looked up once (/rest/api/3/status/{id}) and their category cached.
  6. Commit events and the checkpoint in one batch; advance checked_at only if every result was processed.
  7. Push the events that pass the user's rules (not their own, type enabled, not quiet hours).

How each event type is recognised

EventRuleImportance
assignedbug appears in my list; or a changelog item sets assignee to my account id while already in my list (it left and came back between checks)high
reopenedstatus changes from a done-category status to a not-done one, or to a status named like "Reopen"high
resolved / closedstatus changes into the done category; "closed" if the new name contains "clos"normal
statusany other status changenormal
prioritypriority field changed; escalated if the new one is more urgent by makePriorityRank (then importance high)normal / high
severitythe configured severity field changed (matched by field id or name); escalated by severityRanknormal / high
commenta comment newer than the snapshot; excerpt of 160 characters; at most 5 per bug per checknormal
reassigned_away / unassignedbug left my list and now has another assignee / nonenormal
updatedother field edits, except noise (rank, last viewed, work log…)low (never spoken)

Own actions: if the changelog author or comment author is me, the event is stored with own = true (and as read). It shows in history but is never pushed or spoken.

Why the Blocker bug existed (a real lesson)

The first version ranked priorities by Jira's list order. One real Jira site returned Highest > High > Medium > Low > Lowest > Blocker, so raising a bug to Blocker would have been announced as a downgrade. Now, if every priority name is a familiar word, they are ranked by meaning; only custom names (P1, P2…) use Jira's order. A test covers it.

Guarantees and how they are achieved

GuaranteeMechanism
Never announce old historybaseline on first check; on a new assignment, its whole earlier history is marked seen
Never announce the same change twicestable ids in seen (last 3000 kept), checked before creating an event
Never lose a changewindow based on the last fully processed check; partial runs keep the old checkpoint and are deferred; a 6-hour full comparison repairs anything missed
Correct after restartsall state in D1 (cloud) or jarvis.json (local)
Cheap when nothing happensone search returning nothing, no database write

The Local edition's variant

Locally there is one user and no 50-subrequest limit, so each check lists all assigned bugs and diffs against the snapshot (new, changed, missing). Missing bugs are looked up individually to tell "reassigned" from "aged out". The classification functions are the same ones.

Testing the engine

Both mocks (mock-jira.mjs, mock-atlassian.mjs) can create bugs, assign, change status and priority, comment, and edit, through control endpoints. The test suites then assert the exact event list after each step, for example status:ABC-2, comment:ABC-2 for two changes in one check, and (none) for a repeated check. See How this app is tested.

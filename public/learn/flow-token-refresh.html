Refreshing and rotating tokens

Access tokens expire after about an hour. This is how the Worker gets new ones without asking you to sign in again, and why two requests at the same moment cannot break your connection.

Rotation, and why it is tricky

Atlassian uses rotating refresh tokens: each refresh returns a new refresh token and disables the old one. Re-using an old token outside a 10-minute grace period is treated as theft ("breach detection") and can revoke the whole grant.

Explained simplyImagine a voucher that can be exchanged once for a key card and a new voucher. If two people try to exchange the same voucher, one gets the goods and the other is holding an old voucher. If the old voucher is presented again much later, the shop assumes it was stolen and cancels everything.

Now imagine the cron run and your page request both notice, in the same second, that the access token is about to expire. Without care, both refresh, one of them saves its new tokens last, and the newest refresh token might be overwritten by an older one. That is the race the design prevents.

The solution: a lease and a version number

  1. Still fresh? If the stored access token is valid for more than 2 minutes, decrypt and use it. (This is the normal case: no network call.)
  2. Take a lease: UPDATE … SET lease_until = now+30s WHERE user_id = ? AND version = ? AND lease_until < now RETURNING version. The database guarantees only one caller gets a row back.
  3. Lost the lease? Someone else is refreshing. Wait 0.7 s (then 1.2 s, 1.7 s…) and re-read the row; use the new token when it appears.
  4. Won the lease: decrypt the refresh token, call Atlassian, encrypt the new pair.
  5. Save only if nothing changed: UPDATE … SET enc_tokens = ?, version = version + 1, lease_until = 0 WHERE version = <old>. If zero rows changed (the lease expired and someone else won), re-read and use theirs.

A test fires four requests at once with an expired token: exactly one refresh reaches Atlassian, all four succeed, and the mock's breach detector stays silent.

Belt and braces: 401 during a call

If Jira rejects a token that the database thought was valid (clock skew, early revocation), cloudApi() marks it expired, refreshes once through the same lease logic, and retries the call. A second 401 means access really is gone → reauth.

Key rotation (the encryption key, not OAuth)

To change TOKEN_ENC_KEY without signing everyone out: set the current value as TOKEN_ENC_KEY_OLD and a new TOKEN_ENC_KEY. Decryption tries the new key, then the old one; every refresh re-encrypts with the new key. After a few hours of normal use, everything is on the new key and the old secret can be removed.

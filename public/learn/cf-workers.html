Workers: how your code runs

What a Cloudflare Worker is, how it starts, what it may and may not do, and the handful of rules that shaped every design choice in the Cloud edition.

A Worker is a function, not a server

A traditional server is a program that starts, then waits for requests forever. A Worker is different: Cloudflare keeps your code ready in every data centre, and calls your function when a request (or a cron tick) arrives. Your function returns a response and that is it.

export default {
  async fetch(request, env, ctx) {
    return new Response('Hello from ' + request.cf?.colo);   // the data centre's code, e.g. "BOM"
  },
};
  • request: a standard web Request (URL, method, headers, body).
  • env: your bindings: variables, secrets, the database (env.DB), assets (env.ASSETS).
  • ctx: extras such as ctx.waitUntil(promise) to finish background work after responding.

Isolates: why it starts in milliseconds

Explained simplyA normal server is like renting a whole flat for each guest. Workers are like a hotel with many small rooms in one building: each guest (Worker) gets a sealed room (an isolate) inside the same JavaScript engine (V8, the one in Chrome). Opening a room takes milliseconds; building a flat takes seconds.
  • No cold-start problem worth mentioning; startup must stay under 1 second (this app: 2 ms).
  • An isolate may be reused for several requests, so global variables may survive a while, but you must never rely on that. Anything important goes in D1. (This app only caches harmless things in memory, such as the signed VAPID token.)
  • The runtime is called workerd; wrangler dev runs the same runtime on your computer.

The web platform, not Node.js

Workers implement web standards: fetch, Request/Response, URL, crypto.subtle (Web Crypto), TextEncoder, atob/btoa, streams. Many Node APIs exist behind a compatibility flag, but this project avoids them: the shared core uses only web standards, so the exact same code runs in Node and in workerd.

A real gotchaCloudflare's TypeScript types name the ECDH parameter $public instead of the standard public (because public is a reserved word in their generator). The runtime expects public. The code uses public with a type cast, and a test proves it works by decrypting the result with Node.

Why the Cloud edition looks the way it does

  • 50 subrequests → a Budget object counts every call; D1 writes are batched; the due-users query returns everything in one row per user.
  • 10 ms CPU → at most 12 users per cron run; avoid parsing large responses (field search instead of the full field list; statuses looked up one by one when unknown).
  • No memory between runs → all state in D1.
  • Runs can stop (limits, deploys, crashes) → every step is resumable and idempotent.

Versions and deployments

Every wrangler deploy creates a new version with an id (for example bab7e433-…) and makes it live within seconds worldwide. Old versions are kept, so you can roll back (wrangler rollback). During a deploy, running requests finish on the old version. See Operating in production.

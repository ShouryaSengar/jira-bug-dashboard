The shared Jira core

src/core is the part both servers share: how to ask Jira for bugs, how to shape the answers, and how to turn a changelog into JARVIS events. It uses only web-standard JavaScript, so it runs in Node.js and in a Cloudflare Worker unchanged.

⏱ 10 min readGuide 12 of 47

The key idea: one interface, two implementations

The two editions talk to Jira differently:

  • Local: https://your-site.atlassian.net/rest/api/3/… with Authorization: Basic base64(email:apiToken).
  • Cloud: https://api.atlassian.com/ex/jira/{cloudId}/rest/api/3/… with Authorization: Bearer <OAuth access token>.

Everything else is the same. So the core defines a tiny interface, and each edition provides an object that fulfils it:

export interface JiraApi {
  /** Base URL people open issues on, e.g. https://acme.atlassian.net */
  siteUrl: string;
  /** Stable key for per-site caches. */
  cacheKey: string;
  /** Calls a Jira REST path such as /rest/api/3/myself. Throws HttpError on failure. */
  request(path: string, init?: { method?: 'GET' | 'POST'; body?: unknown }): Promise<Json>;
}
Explained simplyThe core is a recipe that says "ask the kitchen for X". It does not care whether the waiter uses the front door with a key card (Local) or the delivery entrance with a pass (Cloud). Each edition provides its own waiter; the recipe stays the same.

core/jira.ts, function by function

FunctionWhat it does
searchAll(api, jql, fields, max)POSTs to /rest/api/3/search/jql page by page (100 per page, nextPageToken) until done or max reached; reports truncated
getBugs(api, key, opts)Epics view: reads the issue and its links, then searches linkedIssues(key) OR parent = key for the configured issue types; labels each bug's relation ("blocks", "child of"…)
getMyBugs(api, opts)For You: searches assignee = currentUser() (open, or done within N days), adds project, parent, labels, blocked info, latest activity, and "recently assigned" (via assignee CHANGED TO currentUser() AFTER -7d, falling back to created date)
getIssueDetail(api, key, sev)Issue + 30 newest comments + the newest 100 changelog entries in parallel; converts rich text (ADF) to plain text; lists links
recentChangelog(api, key, n)Jira returns history oldest-first; for long histories this jumps to the last page
recentComments(api, key, n)Newest comments first (orderBy=-created)
mapBug(api, issue, sevIds, relation)Turns a raw Jira issue (big, nested) into the app's small Bug object
blockedInfo(fields)Blocked if status sounds blocked, has a blocked label, or an unresolved "is blocked by" link
adfToText(node)Walks the Atlassian Document Format tree: paragraphs, lists, mentions, code, tables, attachments
matchSeverityFields(csv, fields)"Defect Severity, Severity" → field ids such as customfield_12039
makePriorityRank(names)Urgency ranking; if every priority name is familiar (Blocker, Highest, …) rank by meaning, otherwise by Jira's order. Exists because one real site lists "Blocker" last.
severityRank(name)"1 - Critical" < "2 - Major"; falls back to keywords

typesJql(csv)Turns "Bug, Defect" into "Bug","Defect", stripping quotes and backslashes so settings cannot inject JQL

The data shapes it produces

interface Bug {
  key: string; url: string; summary: string; type?: string;
  status: string; statusCategory?: 'new' | 'indeterminate' | 'done';
  priority: string | null; severity: string | null;
  reporter: Person | null; assignee: Person | null;
  created: string; updated: string; resolved: string | null;
  relation: string;                       // "child of", "blocks", "assigned to me"
}
interface MyBug extends Bug {
  project: { key: string; name: string };
  parent: { key: string; summary: string; type?: string } | null;
  labels: string[]; blocked: boolean; blockedReason: string | null;
  recentlyAssigned: boolean;
  lastActivity: { at: string; label: string } | null;
}

core/detect.ts: turning history into events

These functions are pure: the caller fetches the changelog and comments (so it can manage its own request budget) and passes them in. They only decide what the data means.

FunctionInputOutput
classifyNew(ctx, issue, history, lastSync)a bug that just appeared in my listone assigned event (with who did it), or nothing if it is a closed bug merely re-entering the window
classifyChanges(ctx, issue, history, comments, since)a bug whose updated changedstatus / reopened / resolved / closed / priority / severity / assigned / updated / comment events
classifyAway(ctx, issue, prevSummary)a bug no longer assigned to mereassigned_away or unassigned

The context (DetectCtx) supplies: my account id, severity field ids/names, the seen set, a status-category lookup and a priority ranking. Every processed changelog item gets a stable id like ABC-1:h10234:status; comments ABC-1:c55012. Anything in seen is skipped, which makes detection idempotent. Full algorithm: JARVIS: how changes are detected.

Why the core may not import Node or Cloudflare

If core/jira.ts used Buffer (Node) or env.DB (Cloudflare), it would break in the other runtime. Keeping it to standard fetch-free logic plus the injected request() is what lets both editions share it, and lets tests run it in plain Node.

Verified identicalWhen the Local server was refactored onto the core, the old and new versions were run side by side against a real Jira site (read-only): For You, issue detail, an Epics query returning 1009 bugs, and priority ranking produced byte-identical JSON.

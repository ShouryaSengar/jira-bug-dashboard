The cryptography, simply

Every cryptographic building block in the app, what problem it solves, explained without maths, and exactly where it is used. All of it comes from the browser-standard Web Crypto API; nothing is home-made except the assembly.

Hashing: storing sessions

Explained simplyA hash is like a fingerprint of a word. The same word always gives the same fingerprint, but from the fingerprint you cannot rebuild the word.

Your session cookie is 32 random bytes. The database stores SHA-256(cookie). When you make a request, the Worker hashes your cookie and looks up the hash. If someone copies the database, they have fingerprints, not cookies, so they cannot sign in as anyone.

AES-256-GCM: tokens at rest

// cloud/src/crypto.ts (simplified)
const iv = crypto.getRandomValues(new Uint8Array(12));                       // new every time
const ct = await crypto.subtle.encrypt(
  { name: 'AES-GCM', iv, additionalData: enc.encode(`grant:${userId}`) },   // "AAD"
  key, enc.encode(JSON.stringify({ access, refresh })));
store(`${b64url(iv)}.${b64url(ct)}`);
  • The key (TOKEN_ENC_KEY, 32 random bytes) is a Worker secret, not in the database. A database leak alone reveals nothing.
  • A new IV per encryption: encrypting the same tokens twice gives different results, and GCM requires never reusing an IV with the same key.
  • Authenticated: any change to the stored text makes decryption fail instead of producing garbage.
  • Additional data grant:<userId>: not secret, but part of the check. Copying user A's ciphertext into user B's row fails to decrypt. Tested.
  • Key id: the first 8 characters of a hash of the key are stored with the row, so a future rotation can tell which key was used.

Signatures: VAPID

Explained simplyA signature is like a wax seal only you can make (private key) but everyone can recognise (public key). The push service sees the seal and knows the message really comes from this app.

The Worker builds a small JSON Web Token ({"aud": push origin, "exp": in 12 h, "sub": "mailto:…"}), signs header.payload with ECDSA P-256 SHA-256, and caches it for a while. Web Crypto produces the signature in exactly the raw r||s format JWTs need.

Key agreement + derivation: push encryption

ECDH lets the Worker and your browser end up with the same secret number, each using its own private key and the other's public key, without the secret ever crossing the network. HKDF then turns that secret (mixed with your browser's auth secret and a random salt) into an AES key and a nonce. The push service in the middle sees only ciphertext. Full walk-through in Service workers and Web Push.

Constant-time comparison

export function safeEqual(a, b) {
  if (a.length !== b.length) return false;
  let diff = 0;
  for (let i = 0; i < a.length; i++) diff |= a.charCodeAt(i) ^ b.charCodeAt(i);
  return diff === 0;
}

A normal === stops at the first different character, so an attacker measuring response times could guess a secret one character at a time. This version always looks at every character.

What is deliberately not done

  • No custom algorithms; only standard Web Crypto primitives.
  • No encryption keys in code, Git, logs or the database.
  • No "encryption" of things that should simply not be stored (full issue contents are not stored at all).

How correctness is checked

The unit tests round-trip AES-GCM, prove that the wrong user id, a tampered ciphertext or the wrong key all fail, and decrypt Web Push payloads with Node's own crypto module (a completely independent implementation). The end-to-end tests verify VAPID signatures with Node as well.

Service workers and Web Push

How a website can show you a notification when its tab is closed: the service worker that lives in your browser, the push service that delivers messages, and the encryption that keeps them private.

⏱ 11 min readGuide 34 of 47

Service workers

A service worker is a JavaScript file a website registers with your browser:

navigator.serviceWorker.register('sw.js');

Unlike a page, it has no window. The browser starts it when there is something for it to do (a push message, a notification click) and stops it shortly after. It can show notifications, talk to open tabs (postMessage), and fetch from its own origin.

Rules: only on HTTPS (or localhost), scoped to its path (/sw.js covers the whole site), updated when the file changes (Cache-Control: no-cache is set for it).

The parties in Web Push

  1. Subscribe. pushManager.subscribe({ userVisibleOnly: true, applicationServerKey }). The browser asks its push service for an endpoint (a unique URL for this browser and this app) and creates a key pair whose public part (p256dh) and a 16-byte secret (auth) it gives to the page. The page sends all three to the app server.
  2. Send. The app server encrypts a message for those keys and POSTs it to the endpoint, proving its identity with VAPID.
  3. Deliver. The push service keeps the message (up to the TTL) and delivers it when the browser is reachable.
  4. Handle. The browser decrypts it and fires a push event in the service worker, which must show a notification.

VAPID: proving who is sending

Without proof, anyone who learned your endpoint could spam you. VAPID (RFC 8292) fixes this:

  • The app has a key pair (P-256). The public key is given to the browser at subscribe time (applicationServerKey), so the subscription is tied to it.
  • Each send includes Authorization: vapid t=<JWT>, k=<public key>. The JWT says {"aud": "https://fcm.googleapis.com", "exp": …, "sub": "mailto:…"} and is signed with ES256 (ECDSA P-256 SHA-256).
  • The push service verifies the signature with the public key. Only the holder of the private key (a Worker secret) can send to these subscriptions.

Payload encryption (RFC 8291) in plain words

Explained simplyThe browser hands out an open padlock (its public key) and keeps the key. The server makes a fresh one-time padlock of its own, combines the two in a clever way (ECDH) to get a secret only the browser can also work out, uses that secret to lock the message, and sends the locked box plus its own one-time padlock. The post office (push service) carries a box it cannot open.
  1. The server creates a fresh ECDH key pair for this message.
  2. It combines its private key with the browser's p256dh → a shared secret (the browser can compute the same from its side).
  3. HKDF mixes in the auth secret and a random salt to derive a 16-byte content key and a 12-byte nonce.
  4. AES-128-GCM encrypts the JSON (plus a padding delimiter byte).
  5. The body is: salt (16 bytes) + record size (4) + key length (1) + server public key (65) + ciphertext. Header Content-Encoding: aes128gcm.

This app implements it in about 60 lines (cloud/src/push.ts). The test suite decrypts the output with Node's independent crypto implementation to prove it is correct.

Rules browsers enforce

  • Permission first, requested from a user click.
  • userVisibleOnly: true: every push must show a notification. Sites that push silently get their permission revoked (Safari especially), which is why sw.js always shows one.
  • iPhone/iPad: Web Push only for sites added to the Home Screen (iOS 16.4+).
  • Subscriptions can expire: push services return 404/410; the app deletes them. pushsubscriptionchange lets the service worker re-subscribe.

Headers used when sending

HeaderValue here
Authorizationvapid t=…, k=…
Content-Encodingaes128gcm
TTL86400 (hold for a day if the device is offline)
Urgencyhigh for important events, else normal

Safety: the endpoint is user-supplied

A malicious client could submit an "endpoint" pointing at an internal address, hoping the server would send requests there (SSRF). The Worker only accepts HTTPS endpoints whose host is, or ends with, an allow-listed push service: fcm.googleapis.com, updates.push.services.mozilla.com, push.services.mozilla.com, web.push.apple.com, notify.windows.com.

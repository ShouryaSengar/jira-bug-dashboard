Database design (D1)

Every table, column, key and index of the Cloud edition's database, why it exists, and how changes to the structure are rolled out.

⏱ 14 min readGuide 15 of 47
Explained simplyA relational database is a set of spreadsheets (tables). Each row is one thing (a user, a session). A column that points to a row in another table (like user_id) is a foreign key. "ON DELETE CASCADE" means: when the user row is deleted, every row pointing to it is deleted too, automatically.

Entity-relationship diagram

Table by table

users

One row per Atlassian account that has signed in. id is a random UUID (internal, never shown); atlassian_account_id is unique and is how a returning user is recognised. profile_at records when name/email/picture were fetched, for the privacy reports.

sessions

A browser that is signed in. The primary key is the SHA-256 hash of the cookie value, so the database alone cannot be used to impersonate anyone. Expiry is checked on every request (30 days absolute, 7 days idle); expired rows are deleted hourly. Index on user_id (sign out everywhere) and expires_at (cleanup).

oauth_grants

The user's Atlassian tokens, encrypted. One per user because Atlassian issues one grant per app per account. version and lease_until implement safe refresh-token rotation. status becomes revoked when Atlassian refuses a refresh.

jira_sites

Sites the grant can reach, from accessible-resources. Composite primary key (user_id, cloud_id). Replaced on each sign-in.

user_settings

Per-user preferences and monitor schedule. slot (0–59, random at sign-up) spreads users across minutes: a user is due when (minute − slot) mod interval_min = 0. notify_prefs holds the notification rules the server applies to pushes (event types, quiet hours, time zone, frequency, push on/off). severity_ids caches resolved custom field ids (["none"] means "looked up, nothing found").

monitor_state

The JARVIS checkpoint for the active site:

  • snapshot: {"ABC-1": ["2026-11-18T10:00:00.000+0530", "Login fails", "ABC"], …} (updated time, summary, project for each assigned bug)
  • seen: up to 3000 ids of changelog items and comments already turned into events
  • status_cats: status id → category, learned lazily
  • checked_at: last fully processed check (heartbeat every 20 minutes when idle)
  • reconciled_at: last full comparison (every 6 hours)
  • deferred, failures, backoff_until, last_error: scheduling and error handling

events

Notification history, kept 30 days. own marks your own actions (recorded, never pushed, stored as read). pushed tracks delivery so failures are retried: 0 pending, 1 delivered or nothing to deliver, 2 gave up after 6 hours. actor_id lets the privacy job find and scrub names of people whose accounts closed. Indexes: (user_id, id) for history pages, a partial index WHERE pushed = 0 for the retry sweep, and a partial index on actor_id.

push_subscriptions

One per browser/device that enabled background notifications (max 5 per user). endpoint is unique: if another account subscribes the same browser (shared computer), the subscription moves.

rate_limits, pdr_reports, app_meta

Fixed-window counters for sign-in attempts (bucket = hashed IP + 10-minute window); when each account id was last reported to Atlassian; small app-wide values (reporting cycle, back-off).

Important queries

Who is due this minute (one query for all users)

SELECT s.user_id, u.atlassian_account_id, s.active_cloud_id, j.url, …, g.enc_tokens, …, st.snapshot, st.seen, …
FROM user_settings s
JOIN users u        ON u.id = s.user_id
JOIN oauth_grants g ON g.user_id = s.user_id AND g.status = 'active'
JOIN jira_sites j   ON j.user_id = s.user_id AND j.cloud_id = s.active_cloud_id
LEFT JOIN monitor_state st ON st.user_id = s.user_id
WHERE s.monitor_enabled = 1 AND s.monitor_paused = 0 AND COALESCE(st.backoff_until, 0) <= :now
  AND (COALESCE(st.deferred, 0) = 1 OR ((:minute - s.slot) % s.interval_min) = 0)
ORDER BY COALESCE(st.deferred, 0) DESC, ((s.slot * 7919 + :minute) % 1009)
LIMIT 60

Everything a check needs (token, site, snapshot, settings) arrives in this single row, saving subrequests. The odd ordering formula rotates who goes first, so no user is always last.

Atomic sign-in

finishLogin() sends the user upsert, grant upsert, site replacement, settings upsert and session insert as one DB.batch(). D1 runs a batch as a transaction: all succeed or none do.

Safe rotation

UPDATE oauth_grants SET lease_until = :now+30s
WHERE user_id = :u AND version = :v AND lease_until < :now RETURNING version;
-- … refresh at Atlassian …
UPDATE oauth_grants SET enc_tokens = :new, version = version + 1, lease_until = 0
WHERE user_id = :u AND version = :v;

Migrations

The structure is defined by numbered SQL files in cloud/migrations/:

  • 0001_init.sql: all tables above (except the reporting ones).
  • 0002_personal_data_reporting.sql: users.profile_at, events.actor_id, pdr_reports, app_meta.
npx wrangler d1 migrations apply DB --local --env dev          # your computer
npx wrangler d1 migrations apply DB --remote --env production  # Cloudflare

D1 records applied migrations in its own table, so re-running applies only new files. Rules: never edit a migration that already ran in production; add a new numbered file instead; prefer additive changes (new columns with defaults) so old and new code can run side by side during a deploy.

Write budget

D1's free plan allows 100,000 rows written per day. An idle check writes nothing; a heartbeat writes one row every 20 minutes (~72/day/user); each event writes a row (plus index entries); token refreshes write about 24/day/user. Roughly 100–150 rows per active user per day, so about 700–1000 users before writes become the limit, well beyond the CPU limit (~60 users). See The free tier and capacity maths.

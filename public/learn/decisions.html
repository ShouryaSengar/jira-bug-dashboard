Design decisions and trade-offs

Every important "why" in one place, written as short decision records: the situation, the options, the choice, and what it costs.

⏱ 12 min readGuide 8 of 47
Why write decisions downSix months from now nobody remembers why something is the way it is. A decision record stops future you from "fixing" a deliberate choice, and shows what to revisit when circumstances change (for example, moving to a paid plan).

D1. A server is required (no browser-only app)

Situation. Jira Cloud's REST API does not support cross-origin browser requests with credentials (CORS), and tokens in a page are easy to steal.
Choice. Every edition with real data has a server: Node.js locally, a Cloudflare Worker in the cloud. The demo edition has no server and no real data.
Cost. Something must be hosted. Mitigated by free hosting (Cloudflare) and the Local option.

D2. Cloudflare Workers + Static Assets for the Cloud edition

Options. Render / Fly / Railway (a normal always-on server), Vercel/Netlify functions, Cloudflare Pages + a separate Worker, one Worker with static assets.
Choice. One Worker serving the static app and the API. Asset requests are free and unlimited; one deployment, one URL, one config.
Why not an always-on server? Free tiers there sleep after inactivity (so background monitoring stops) or no longer exist. Workers never sleep: the cron wakes them.
Cost. Strict per-run limits on the free plan (10 ms CPU, 50 subrequests). The design works around them (D7).

D3. D1 as the only database

Options. KV (key-value), Durable Objects, D1 (SQL), an external database.
Choice. D1. The data is relational (users → sessions, grants, settings, events, devices), needs per-user filtering, foreign keys, indexes and atomic batches. KV is eventually consistent and lacks queries; Durable Objects are powerful but unnecessary here.
Cost. 100,000 rows written per day on the free plan, so idle checks must write nothing (they do).

D4. Polling Jira instead of webhooks

Options. Jira webhooks (Jira calls us when something changes) or polling (we ask Jira regularly).
Choice. Polling with an incremental query. For OAuth (3LO) apps, dynamic webhooks are limited (they expire, have filter restrictions, require the app to manage registrations per user and site), and the Local edition on localhost cannot receive webhooks at all. One polling design serves both editions.
Cost. Up to one interval of delay (5 minutes by default in the cloud). Accepted for a bug dashboard.

D5. Detect events from the changelog, not from timestamps

Situation. Jira's updated field says that something changed, not what.
Choice. updated is only the trigger. The changelog and comments are read, and each item's stable id is recorded in seen, so the same change can never be announced twice, even across restarts or overlapping windows.
Cost. Two extra API calls per changed bug. Unchanged bugs cost nothing.

D6. Incremental JQL window

Choice. Each check runs one query:

issuetype in ("Bug") AND (
  (assignee = currentUser() AND updated >= -Nm)
  OR assignee CHANGED FROM currentUser() AFTER -Nm
) ORDER BY updated ASC

Relative windows (-Nm) avoid time-zone mistakes (absolute dates in JQL are interpreted in the user's Jira time zone). The CHANGED FROM part catches bugs handed to someone else without an extra lookup. A full comparison runs every 6 hours to repair drift.
Cost. Depends on Jira's assignee history being searchable (it is, on Jira Cloud).

D7. Budgeted, resumable cron runs

Choice. Every outgoing call (Jira, Atlassian, D1, push) goes through a Budget object; runs are capped at 12 users; users that do not fit are marked deferred and handled first next minute. The checkpoint only advances when a user's changes were fully processed.
Cost. About 60 users at a 5-minute interval on the free plan. More users means slower checks, never lost events.

D8. Sign in with Atlassian (OAuth 3LO), no passwords

Options. Users paste API tokens into the cloud; our own accounts with passwords; OAuth.
Choice. OAuth only. The Atlassian account is the identity. No passwords to store; scopes are read-only; users can revoke access at Atlassian.
Cost. Requires registering an app, rotating refresh tokens, and Atlassian's privacy obligations (D12).

D9. Encrypt tokens with a key outside the database

Choice. AES-256-GCM with TOKEN_ENC_KEY (a Worker secret). The ciphertext is bound to the user id (additional authenticated data), so a row copied to another user cannot be decrypted.
Cost. Losing the key means everyone must sign in again. Rotation is supported with TOKEN_ENC_KEY_OLD.

D10. No frontend framework

Choice. Plain TypeScript modules, HTML templates as strings (always escaped), CSS variables for themes, SVG charts drawn by hand.
Why. The app is small enough; zero dependencies means zero supply-chain risk, tiny downloads, and the same files run on three hosts without a build server. A React/PWA migration is on the roadmap as a separate phase.
Cost. Re-rendering is manual; more care is needed to keep DOM updates tidy.

D11. Web Push implemented by hand

Choice. VAPID signing (RFC 8292) and payload encryption (RFC 8291) written with Web Crypto, about 150 lines, instead of an npm library.
Why. Popular libraries depend on Node's crypto module; Workers have Web Crypto. Fewer dependencies, smaller bundle, CPU measured at about 0.45 ms per message.
Cost. We own correctness; it is verified by decrypting real output with Node's independent crypto in the tests.

D12. Report personal data to Atlassian

Situation. Apps that store personal data (account ids, names) must use Atlassian's Personal Data Reporting API.
Choice. Store actor account ids with history so they can be reported; report every stored account weekly; erase on closed, clear on updated; erase whole accounts 30 days after access ended.
Cost. One extra table and a few requests per week.

D13. Same API contract for Local and Cloud

Choice. The Worker answers /api/config, /api/bugs, /api/mine, /api/issue, /api/jarvis/* with the same shapes as the Node server. Cloud-only features live under new paths.
Why. The frontend needed only a third "mode", not a rewrite; local behaviour stayed byte-identical (verified).

D14. Live delivery: SSE locally, Web Push in the cloud

Situation. A Worker run ends after its request; it cannot keep a stream open for minutes waiting for the next cron run without Durable Objects.
Choice. The cloud delivers live events through push (the service worker relays them to open tabs). Opening or returning to the tab fetches anything missed. No polling loop in the browser.
Cost. If a user declines notification permission, live updates arrive when they return to the tab or press "Check now".

D15. Voice only while a tab is open

Browsers do not allow speech from a closed tab or a service worker, so the app does not pretend. Notifications cover the closed-browser case; voice happens when a dashboard tab is open.

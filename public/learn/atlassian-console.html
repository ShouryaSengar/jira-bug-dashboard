The developer console, sharing and privacy duties

Registering an OAuth app with Atlassian, every setting that matters, how to let other people sign in, and the Personal Data Reporting obligation that comes with storing personal data.

Registering the app

  1. Open developer.atlassian.com/console/myapps and sign in.
  2. Create → OAuth 2.0 integration, give it a name, accept the terms.
  3. Permissions: add Jira API → Configure → classic scopes read:jira-work, read:jira-user. Add User identity API (read:me).
  4. Authorization → OAuth 2.0 (3LO): enter the callback URL exactly, for example https://jira-bug-dashboard-cloud.shouryacode2021.workers.dev/auth/callback. Choose Resource-level access.
  5. Settings: copy the Client ID (public; goes in wrangler.jsonc) and the Secret (private; goes straight into wrangler secret put ATLASSIAN_CLIENT_SECRET, never into a file or chat).
The greyed-out Save buttonThe console only enables "Save changes" when the text differs from what is saved. If the URL is already saved, the button stays grey. That is not an error. The "Authorization URL generator" on the same page shows the saved value inside its links: check that redirect_uri ends with %2Fauth%2Fcallback.
offline_access is not in the consoleYou will not find offline_access among the scopes to tick. The app adds it to the authorize URL itself; that is how Atlassian works.

The personal-data declaration

Atlassian asks: does your app store personal data? "Yes" if you copy and keep data linked to user references (such as account ids) or cache data for longer than 24 hours. This app does (names, emails, account ids in history for 30 days), so the answer is Yes, which brings an obligation:

The Personal Data Reporting API

Apps that store personal data must regularly tell Atlassian which accounts they hold data for. Atlassian then replies, per account, whether the person closed their account or changed their data.

POST https://api.atlassian.com/app/report-accounts/
Authorization: Bearer <an access token of this app>
{ "accounts": [
    { "accountId": "5b10ac8d…", "updatedAt": "2026-11-18T19:37:44.066Z" },
    …  up to 90 per request
] }

204 No Content            → nothing to do
200 { "accounts": [ { "accountId": "…", "status": "closed" },
                    { "accountId": "…", "status": "updated" } ] }
429 + Retry-After         → slow down
  • Cycle: every 7 days by default (or what the Cycle-Period header says); not more often.
  • updatedAt: when you fetched that person's data (the oldest, if several pieces).
  • closed: erase everything about that person. updated: your copy is stale; refresh or erase it.
  • Never report the special id unknown. Do not schedule exactly on the hour (everyone does).

How this app implements it (minute :37, resumable, erases and scrubs): Privacy and the data life cycle. Its first real report was accepted by Atlassian on 18 November 2026.

Checklist for any Atlassian OAuth app

  • ☐ Scopes as narrow as possible (read-only if you can)
  • ☐ Callback URL exact, HTTPS
  • ☐ state parameter bound to the browser
  • ☐ Client secret only in server secrets
  • ☐ Rotating refresh tokens handled without races
  • ☐ invalid_grant → ask the user to reconnect
  • ☐ Privacy policy published
  • ☐ Personal Data Reporting implemented if you store personal data
  • ☐ Data erased when no longer needed (revocation, account closed)

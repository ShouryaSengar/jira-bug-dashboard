Local server internals

The Local edition's backend: a single Node.js process on your own computer that serves the page, talks to Jira with your API token, and runs JARVIS in the background.

⏱ 10 min readGuide 13 of 47

What starts when you run npm start

  1. tsc compiles src/ into dist/.
  2. node dist/server/index.js starts an HTTP server on 127.0.0.1:4545 (only your own computer can reach it).
  3. monitor.start() schedules the first JARVIS check 1.5 seconds later, then every 60 seconds.
  4. It prints which credentials it uses: environment variables or ~/.jira-bug-dashboard/config.json.

How it protects you even on localhost

  • Binds to 127.0.0.1: other machines on your Wi-Fi cannot connect.
  • Host check: requests must say Host: localhost:4545 or 127.0.0.1:4545. This defeats "DNS rebinding", a trick where a malicious website points its own domain at 127.0.0.1.
  • Origin + custom header on every non-GET request, so another website open in your browser cannot change settings.
  • Credentials file in your home folder with permission 0600 (only your user can read it), never in the project folder, so it cannot be committed to Git.
  • System notifications are sent with execFile and an argument list, never through a shell, so text from Jira cannot become a command.

The local monitor (src/server/jarvis.ts)

A simpler cousin of the cloud monitor, because it runs for one user with no strict limits:

  1. Every interval (30 s to 15 min, default 60 s): one paginated search lists every bug assigned to you.
  2. The list is compared with the previous snapshot: new keys → classifyNew; changed updated → read changelog and comments → classifyChanges; keys that disappeared → look the issue up → classifyAway.
  3. Events get increasing ids, are appended to the history (max 500), and are written with the snapshot and seen ids to jarvis.json atomically (write a temporary file, then rename).
  4. Each connected browser tab receives the events over its open SSE connection; status updates are sent too.
  5. If no tab is connected and you enabled it, macOS (osascript) or Linux (notify-send) shows a system notification.
  6. Failures back off exponentially (honouring Jira's Retry-After); bad credentials wait 10 minutes.

The classification functions are the shared ones in src/core/detect.ts, so both editions announce exactly the same things. See JARVIS: how changes are detected.

Server-Sent Events in 30 seconds

The browser opens new EventSource('api/jarvis/stream'). The server answers with Content-Type: text/event-stream and never closes the response. Whenever it has news it writes:

id: 42
event: jarvis
data: {"id":42,"type":"comment","key":"ABC-1",…}

The browser reconnects automatically if the connection drops and sends Last-Event-ID, so the server replays what was missed. A comment line (: ping) every 25 seconds keeps proxies from closing the idle connection.

Cloud Worker internals

Every file of the Cloudflare Worker, what it does, and how a request or a cron tick travels through it.

⏱ 16 min readGuide 14 of 47

The two doors into the Worker

A Worker is a JavaScript module that exports handlers. Cloudflare calls them:

// cloud/src/index.ts
export default {
  async fetch(req, env) {                         // every HTTP request
    const url = new URL(req.url);
    if (url.pathname.startsWith('/api/') || url.pathname.startsWith('/auth/')) {
      try { assertConfigured(env); return await handleApi(req, env, url); }
      catch (e) { return errorResponse(e); }
    }
    return env.ASSETS.fetch(req);                 // everything else: static files
  },
  async scheduled(event, env, ctx) {              // the cron trigger, every minute
    ctx.waitUntil(runTick(env, event.scheduledTime).then(logSummary));
  },
};
Static files usually skip the WorkerWith run_worker_first: ["/api/*", "/auth/*"] in wrangler.jsonc, Cloudflare serves files such as /index.html or /js/main.js directly from its asset storage. Those requests are free and do not count against the 100,000 daily Worker requests. Only API and sign-in paths run our code.

A request's path through the files

File by file

env.ts: configuration

Declares every binding (DB, ASSETS), variable (APP_ORIGIN, ATLASSIAN_CLIENT_ID, PUSH_ENDPOINT_HOSTS, limits) and secret (ATLASSIAN_CLIENT_SECRET, TOKEN_ENC_KEY, VAPID_PRIVATE_KEY, VAPID_SUBJECT). assertConfigured() answers 503 "Cloud edition is not configured: missing …" (names only, never values) until everything is set, so a half-configured deployment cannot accept sign-ins.

http.ts: the web plumbing

  • json(), redirect() add security headers (nosniff, DENY framing, no referrer, no-store, HSTS).
  • errorResponse() turns known errors into clean JSON, and unknown ones into a generic 500 (the details go to the log, not to the user).
  • cookie() always sets Path=/; HttpOnly; Secure; SameSite=Lax for __Host- cookies.
  • assertSameOrigin(): the CSRF guard (Origin, Sec-Fetch-Site, X-JBD: 1).
  • readJson(): refuses bodies over 16 KB and invalid JSON.
  • rateLimit(): a per-isolate token counter (a speed bump, not a global quota).

crypto.ts: small, careful helpers

base64url encoding, random tokens (crypto.getRandomValues), SHA-256, constant-time comparison, and encryptJson/decryptJson with AES-256-GCM, a random 12-byte IV per encryption and additional authenticated data grant:<userId>. See The cryptography, simply.

auth.ts: identity and tokens

  • startLogin(): per-IP sign-in limit (D1), random state in an HttpOnly cookie, redirect to auth.atlassian.com/authorize with four scopes.
  • finishLogin(): checks state (constant time), exchanges the code, checks the granted scopes, reads /me and accessible-resources, then in one batch upserts the user, stores the encrypted grant, replaces the sites, creates settings and a session.
  • getSession(): hashes the cookie, finds the session; enforces 30-day absolute and 7-day idle expiry; slides the idle timer at most once an hour.
  • accessToken(): returns a valid access token, refreshing with a lease and a version check (details).
  • cloudApi(): the cloud implementation of the core's JiraApi, retrying once after forcing a refresh on 401.

api.ts: the endpoints

One router (handleApi) with a switch on "METHOD /path". Sign-in routes come first (they are top-level navigations), then the CSRF check, then /api/config (works signed-out), then requireSession() and a per-user rate limit for everything else. All endpoints are listed in the API reference.

monitor.ts: the cron engine

runTick() loads due users in one query, checks each (checkUser), defers whoever does not fit, retries pending pushes, runs the privacy report at minute :37 and housekeeping at minute :13. Each user check is incremental and writes nothing when idle. Complete walkthrough: The background check and JARVIS engine.

budget.ts: staying under 50 subrequests

export class Budget {
  used = 0;
  constructor(public readonly size: number) {}
  get left() { return this.size - this.used; }
  has(n: number) { return this.left >= n; }
  take(n = 1) { if (this.used + n > this.size) throw new BudgetExhausted(); this.used += n; }
}

Every fetch to Atlassian or a push service and every D1 call calls budget.take() first. If a user's work does not fit, BudgetExhausted is caught, the user is marked deferred, and nothing half-done is committed.

push.ts: Web Push

endpointAllowed() (HTTPS + allow-listed push hosts), vapidJwt() (ES256-signed, cached 12 hours per push origin), encryptPayload() (RFC 8291) and sendPush() (maps 404/410 to "gone" so dead subscriptions are deleted). See Service workers and Web Push.

privacy.ts: Personal Data Reporting

Lists every stored account id, reports up to 90 per request to Atlassian, erases on closed, clears on updated. See Privacy and the data life cycle.

cloud/public/sw.js: the service worker

Not part of the Worker (it runs in the browser), but deployed with it. Handles push (show notifications, forward events to open tabs), notificationclick (focus or open the dashboard at the bug), and pushsubscriptionchange (re-register).

Configuration file: wrangler.jsonc

{
  "name": "jira-bug-dashboard-cloud",
  "main": "src/index.ts",
  "compatibility_date": "2026-11-01",
  "assets": { "directory": "./dist-assets", "binding": "ASSETS", "run_worker_first": ["/api/*", "/auth/*"] },
  "env": {
    "dev":        { "vars": { … mock URLs … }, "d1_databases": [ … local … ], "triggers": { "crons": ["* * * * *"] } },
    "production": { "vars": { "APP_ORIGIN": "https://…workers.dev", "ATLASSIAN_CLIENT_ID": "…", … },
                    "d1_databases": [{ "binding": "DB", "database_name": "jbd-cloud", "database_id": "…" }],
                    "triggers": { "crons": ["* * * * *"] } }
  }
}

Each environment has its own bindings, variables and triggers (they are not inherited). Secrets are not in this file at all. More in D1, assets, cron, secrets and environments.

What the Worker never does

  • Return or log tokens (the logs show request URLs with the OAuth code and state redacted by Cloudflare).
  • Trust a user id or site id from the client: the site must belong to the session's user.
  • Store Jira issue contents beyond what monitoring and history need.
  • Keep state between runs in memory (except harmless caches such as the VAPID JWT).

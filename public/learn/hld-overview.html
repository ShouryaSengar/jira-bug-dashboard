High-level design

The big boxes of the system, what each is responsible for, and how data moves between them. This is the "HLD": the view an architect draws first.

⏱ 12 min readGuide 7 of 47
Explained simplyA high-level design is like a city map that shows districts and main roads, but not every house. Low-level design (the next category) is the street map.

Context: the system and its neighbours

Start from the outside. What is inside "our system", and what do we depend on?

The main data flows

1. Reading (on demand)

Browser → GET /api/mine with session cookie → Worker finds the session in D1 → decrypts the user's access token → calls Jira through api.atlassian.com → maps the result to a small, clean shape → returns JSON → browser renders. Nothing from Jira is stored except a cache in the user's own browser. Details: Loading "For You".

2. Watching (scheduled)

Cron → Worker loads the users due this minute (one query) → for each: one small JQL search for what changed → reads changelog/comments only for changed bugs → turns them into events → one batched write → Web Push to the user's devices. Details: The background check.

3. Notifying (asynchronous)

Worker → encrypted message → browser maker's push service → the user's browser → service worker shows a notification and forwards the events to open tabs → JARVIS speaks. Details: A notification's journey.

4. Authorising (once, then silently)

Browser → /auth/login → Atlassian consent → /auth/callback → Worker exchanges the code for tokens, encrypts and stores them, creates a session. Later, tokens are refreshed automatically. Details: Signing in and Refreshing tokens.

Deployment view

The Local edition in the same picture

Replace "Cloudflare Worker + D1 + cron" with "a Node.js process on your computer + a JSON file + a timer", replace OAuth with your own API token, and replace Web Push with a Server-Sent Events stream. Everything else (frontend, shared core, JARVIS rules) is identical. See Local server internals.

Key properties of this design

  • Stateless compute, stateful database. A Worker keeps nothing between runs. Every fact that must survive lives in D1. That is what makes it safe to run thousands of copies and to restart any time.
  • Pull for data, push for news. Pages pull data when you look; notifications are pushed when something happens.
  • Incremental everything. The monitor asks only "what changed since last time", writes only when something changed, and stops cleanly when it runs out of budget, resuming next minute.
  • Least privilege. Read-only Jira scopes; each user's token is used only for that user; resource-level grants limit access to the chosen site.
